# Telepass — یوزربات فیلتر و فوروارد تلگرام

پروژهٔ **Node.js + SQLite** برای ورود با **اکانت شخصی**، رصد زندهٔ گروه‌ها/کانال‌های انتخابی و فوروارد پیام‌های اشخاص یا کانال‌های مجاز به یک مقصد. مدیریت فقط با اکانت تلگرام دارای ID ثابت **`8583719429`** و فقط در چت خصوصی انجام می‌شود.

> این پروژه Bot API نیست و به توکن BotFather نیاز ندارد. اکانت اجراکننده باید **جدا از اکانت ادمین** باشد. کد تأیید و رمز دومرحله‌ای را فقط در ترمینال امن خودتان وارد کنید، نه در چت یا تیکت پشتیبانی.

## امکانات

- MTProto با **Teleproto**، فورک نگه‌داری‌شده و سازگار با GramJS؛ بدون مرورگر یا شبیه‌سازی رابط تلگرام.
- ورود اولیه با شماره، کد تأیید و در صورت فعال بودن، رمز دومرحله‌ای؛ اتصال‌های بعدی با نشست ذخیره‌شده، بدون درخواست مجدد کد.
- مبدأها، وایت‌لیست، تنظیمات و صف ارسال در SQLite داخلی Node.js؛ بدون سرور دیتابیس یا نصب افزونهٔ native.
- منوی متنی فارسی، افزودن/حذف/نمایش و صفحه‌بندی، نمایش نام + یوزرنیم + ID + ورودی اولیه.
- پذیرش `@username`، یوزرنیم ساده، لینک عمومی، لینک دعوت، لینک پیام و ID عددی شناخته‌شده.
- دو تنظیم **مستقل برای هر قانون**: ارسال پیام ازقبل‌فورواردشده و ارسال اصل پیام ریپلای‌شده.
- صف پایدار، ارسال ترتیبی با فاصلهٔ حداقل ۱٫۲ ثانیه، تلاش مجدد و رعایت FloodWait/SlowMode تلگرام.
- جلوگیری از یکسان بودن مبدأ و مقصد، حذف تکراری‌ها و استفاده از `random_id` ثابت برای تلاش مجدد در تلگرام.
- بدون دانلود فایل/رسانه؛ فقط شناسهٔ پیام و اطلاعات مسیر در دیتابیس ذخیره می‌شود، نه محتوای پیام‌ها.
- سقف صف ۵۰۰۰ کار؛ نگه‌داری نتیجهٔ کارها حداکثر ۷ روز / ۲۰۰۰۰ مورد، پاک‌سازی دوره‌ای و cache محدود.
- قفل تک‌پردازشی، خاتمهٔ امن، Docker، systemd و health check اختیاری.

## پیش‌نیاز

- **Node.js 24 LTS پیشنهاد می‌شود**؛ حداقل `22.13.0` با `node:sqlite`. هشدار experimental در Node 22 ممکن است نمایش داده شود و به‌تنهایی خطا نیست.
- یک شماره و اکانت شخصی که مالک آن هستید و به گروه‌های مبدأ دسترسی دارد.
- `API ID` و `API HASH` برنامهٔ خودتان از <https://my.telegram.org> → API development tools.
- ارتباط خروجی MTProto با سرورهای تلگرام و پوشهٔ قابل نوشتن و **دائمی** برای `DATA_DIR`.
- اکانت اجراکننده در کانال مقصد باید مجوز **ارسال پست** داشته باشد؛ برای پیوی/گروه مقصد، امکان ارسال پیام لازم است.

## راه‌اندازی سریع

```bash
npm ci --omit=dev
cp .env.example .env
# .env را در ویرایشگر محلی با مشخصات واقعی خودتان تکمیل کنید.
chmod 600 .env
npm run login
npm start
```

محتوای `.env`:

```dotenv
TELEGRAM_API_ID=YOUR_NUMERIC_API_ID
TELEGRAM_API_HASH=YOUR_32_CHARACTER_API_HASH
TELEGRAM_PHONE=+989123456789
DATA_DIR=./data
# فقط برای میزبان بدون ترمینال/دیسک دائمی (Botkeep، Faable، Render، …):
# TELEGRAM_SESSION=
# فقط اگر میزبان پورت HTTP می‌خواهد:
# PORT=8080
```

### ورود بدون ترمینال: `TELEGRAM_SESSION`

بسیاری از میزبان‌های رایگان نه ترمینال تعاملی دارند و نه دیسک دائمی؛ در نتیجه `npm run login` روی آن‌ها اجرا نمی‌شود. برای این حالت، نشست را **یک‌بار روی رایانهٔ خودتان** بسازید و فقط رشتهٔ نشست را به میزبان بدهید:

```bash
# روی رایانهٔ محلی، در همان پوشهٔ پروژه:
npm run login -- --print-session
# خروجی، یک خط با عنوان TELEGRAM_SESSION چاپ می‌کند.
```

سپس در پنل میزبان متغیر محیطی `TELEGRAM_SESSION` را با همان مقدار (محرمانه/Secret) تنظیم کنید. برنامه در `npm start` اول `TELEGRAM_SESSION` را می‌خواند و اگر نبود، `DATA_DIR/session.txt` را. اگر هر دو موجود و متفاوت باشند، اجرا با پیام واضح متوقف می‌شود تا نشست اشتباه استفاده نشود. `TELEGRAM_SESSION` مثل رمز عبور است: در Git، چت، اسکرین‌شات یا لاگ قرار نگیرد. با `npm run login` (بدون سوییچ) همان نشست در `data/session.txt` ذخیره می‌شود؛ برای VPS و Docker همین فایل کافی است.

`npm run login` به ترمینال تعاملی نیاز دارد. تلگرام روش تحویل کد را تعیین می‌کند؛ کد ممکن است در برنامهٔ تلگرام برسد، نه SMS. کد و رمز هنگام ورود نمایش داده نمی‌شوند و ذخیره نمی‌شوند. فایل حساس `data/session.txt` پس از ورود موفق ایجاد می‌شود. ورود اشتباه یا منقضی‌شده را با اجرای مجدد دستور اصلاح کنید.

نشست ذخیره‌شده به معنی دسترسی به اکانت است؛ آن را مثل رمز عبور نگه دارید. `.env` و کل `data/` از Git و ایمیج Docker حذف شده‌اند. `API HASH`، شماره یا نشست را در کد قرار ندهید.

از اکانت ادمین `8583719429` به **پیوی اکانت اجراکننده** پیام `/menu` بفرستید. برنامه برای پیوی دیگران، دستورهای داخل گروه و پیام‌های خروجی خودش پاسخ مدیریتی نمی‌فرستد.

### نمونهٔ پیکربندی

هر خط را در یک پیام جدا بفرستید و منتظر پاسخ بمانید:

```text
/destination set @my_destination_channel
/join https://t.me/my_source_group
/source add @my_source_group
/allow add @selected_person
/allow list
/rule 1 forwards off
/rule 1 replies on
/status
```

شمارهٔ `1` در مثال، **شمارهٔ قانون** در `/allow list` است، نه ID تلگرام شخص.

برای رصد پست‌های یک کانال به‌عنوان فرستندهٔ مجاز:

```text
/join https://t.me/source_channel
/source add @source_channel
/allow add @source_channel
/allow list
/rule 2 forwards off
```

شمارهٔ قانون را از فهرست واقعی بگیرید. در این حالت پست‌های عادی کانال ارسال می‌شوند، ولی پست‌هایی که خودشان فوروارد از جای دیگرند ارسال نمی‌شوند. برای تغییر همین رفتار، `forwards on` را بفرستید.

## منو و دستورها

اکانت شخصی امکان ساخت کیبورد اینلاینِ مخصوص Bot API را ندارد؛ منو عمداً **متنی و شماره‌دار** است. اعداد فارسی و انگلیسی منو پذیرفته می‌شوند. افزودن/حذف از منو یک ورودی بعدی می‌گیرد؛ `/cancel` لغو و `/menu` بازگشت است. مهلت هر ورودی ۵ دقیقه است. هنگام اجرای یک دستور طولانی، پیام مدیریتی هم‌زمان دیگری پردازش نمی‌شود؛ منتظر پاسخ بمانید.

| دستور | کاربرد |
|---|---|
| `/menu` یا `/start` | منوی اصلی |
| `/help` | راهنما |
| `/status` | اتصال، مبدأها، قوانین، RAM، صف و تعداد رویدادهای ردشده به علت پر بودن صف |
| `/source list [PAGE]` | نمایش مبدأها، ۱۲ مورد در هر صفحه |
| `/source add REF` | افزودن گروه/کانال مبدأ |
| `/source remove ID` | حذف مبدأ با ID کامل نمایش‌داده‌شده و لغو کارهای منتظر آن |
| `/allow list [PAGE]` | نمایش وایت‌لیست و شماره و تنظیمات هر قانون |
| `/allow add REF` | افزودن شخص یا کانال به وایت‌لیست؛ افزودن دوباره تنظیمات قبلی را حفظ می‌کند |
| `/allow remove NUMBER` | حذف قانون با شمارهٔ داخلی و لغو کارهای منتظر آن |
| `/rule NUMBER forwards on` | مجاز کردن پیام‌های ازقبل‌فورواردشده؛ پیش‌فرض روشن |
| `/rule NUMBER forwards off` | حذف پیام‌های ازقبل‌فورواردشده از فیلتر |
| `/rule NUMBER replies on` | ابتدا اصل پیام ریپلای‌شده، سپس پاسخ شخص؛ پیش‌فرض خاموش |
| `/rule NUMBER replies off` | فقط خود پیام شخص |
| `/destination set REF` | تست واقعی ارسال و سپس ذخیرهٔ مقصد |
| `/destination show` | نمایش مقصد |
| `/join LINK_OR_USERNAME` | عضویت صریح در گروه/کانال |
| `/sync` | شناسایی موجودیت‌های حداکثر ۲۰۰ گفتگوی اخیر برای دسترسی با ID |
| `/pause` | توقف دریافت جدید و ارسال صف |
| `/resume` | ادامهٔ دریافت و ارسال |
| `/errors` | ده خطای نهایی اخیر ارسال با شناسهٔ مبدأ/پیام |
| `/queue clear confirm` | حذف غیرقابل‌بازگشت کارهای منتظر |
| `/cancel` | لغو ورودی منو |

`REF` می‌تواند `@username`، `https://t.me/name`، `t.me/+INVITE`، `t.me/joinchat/INVITE` یا ID باشد. لینک پیام `t.me/name/123` به گفتگوی مربوطه و `t.me/c/1234567890/123` به کانال `-1001234567890` تبدیل می‌شود؛ شمارهٔ پیام در این لینک‌ها برای تنظیم موجودیت است، نه وارد کردن تاریخچه. شمارهٔ تلفن با `+` هم فقط در صورتی قابل حل است که تلگرام آن مخاطب را برای این اکانت قابل شناسایی بداند.

### نکات مهم شناسه و فیلتر

- **فقط ID عددی همیشه کافی نیست.** تلگرام برای شخص/کانال `access_hash` می‌خواهد؛ اگر اکانت موجودیت را نشناسد، از یوزرنیم/لینک استفاده کنید یا `/sync` بفرستید. ID و access hash به‌صورت رشته ذخیره می‌شوند تا دقتشان از بین نرود.
- `add` عمداً باعث عضویت پنهانی نمی‌شود. برای لینک دعوت ابتدا `/join LINK` بفرستید. اگر عضویت نیازمند تأیید است، پس از تأیید دوباره مبدأ را اضافه کنید. برنامه درخواست عضویت را دور نمی‌زند.
- شرط ارسال: **مبدأ ثبت شده + فرستندهٔ قابل مشاهده در وایت‌لیست + مقصد تنظیم شده + برنامه متوقف نباشد**.
- مبدأ اصلیِ یک پیام فورواردشده هویت فرستندهٔ فعلی محسوب نمی‌شود؛ کسی با فوروارد کردن پست فرد مجاز، وارد وایت‌لیست نمی‌شود.
- در کانال، هویت فرستنده معمولاً خود کانال است. ادمین ناشناس گروه یا شخصی که با هویت کانال ارسال می‌کند را نمی‌توان با ID شخصی پنهان‌شده تشخیص داد. گروه/سوپرگروه به‌عنوان «شخص وایت‌لیست» پذیرفته نمی‌شود، اما به‌عنوان مبدأ پذیرفته می‌شود.
- گزینهٔ `replies` فقط برای قانون شخص است. اصل پیام ممکن است از **شخص غیرمجاز** باشد و صرفاً به‌عنوان زمینهٔ پاسخ ارسال می‌شود؛ این افشای زمینه را آگاهانه فعال کنید. ریپلای بین دو چت و سرآیند خودِ تاپیک انجمن ارسال نمی‌شوند؛ ریپلای واقعی داخل تاپیک پشتیبانی می‌شود.
- تغییر گزینه‌ها برای پیام‌های بعدی است. حذف مبدأ/قانون و پاک‌کردن صف، کارهای منتظر را لغو می‌کند، ولی ارسال در حال اجرای شبکه ممکن است تمام شود.
- تا زمانی که صف خالی نشده، تغییر مقصد به جای دیگری ممنوع است؛ کارهای صف مسیر ثبت‌شدهٔ خود را حفظ می‌کنند.

## استقرار روی botkeep.cloud

**اتصال واقعی به پنل botkeep.cloud و استقرار در آن در این محیط انجام نشده است.** مراحل زیر نیازمندی‌های استاندارد این پروژه‌اند؛ نام دکمه‌ها و امکانات دقیق پلن باید از پنل/پشتیبانی سرویس بررسی شوند.

1. محیط **Node.js 24** (یا حداقل 22.13) انتخاب کنید. اگر فقط Bot API / توکن ربات را پشتیبانی می‌کند، مناسب این پروژه نیست؛ اجرای پردازش دلخواه Node.js/MTProto لازم است.
2. فایل‌های پروژه شامل `package.json`، `package-lock.json` و `src/` را بارگذاری کنید. `node_modules` را از رایانهٔ خود آپلود نکنید.
3. دستور نصب: `npm ci --omit=dev`. دستور اجرا: `npm start`. مسیر کاری باید ریشهٔ پروژه باشد.
4. `TELEGRAM_API_ID` و `TELEGRAM_API_HASH` را در بخش متغیرهای محیطی/Secrets تنظیم کنید. `DATA_DIR` را به مسیر فضای دائمی قابل نوشتن همان سرویس بدهید.
5. اگر ترمینال تعاملی دارد: موقتاً سرویس را متوقف و `npm run login` را اجرا کنید، سپس سرویس را با `npm start` روشن کنید.
6. اگر ترمینال ندارد: روی رایانه/سرور مطمئن با همین API ID/HASH `npm run login -- --print-session` را انجام دهید و رشتهٔ چاپ‌شده را در متغیر محرمانهٔ `TELEGRAM_SESSION` همان سرویس بگذارید (راه دیگر: انتقال امن **فقط `data/session.txt`** به پوشهٔ دائمی `DATA_DIR`). نشست را داخل متغیر عمومی، Git یا لاگ نگذارید. در اولین اجرا SQLite ساخته می‌شود.
7. **Auto restart / Always on** را فعال کنید و فقط **یک replica** داشته باشید. پس از کرش، برای انقضای قفل تک‌پردازشی ممکن است ۳۰ ثانیه لازم باشد.
8. این برنامه برای عملکرد اصلی پورت ورودی لازم ندارد. اگر سرویس پورت می‌خواهد، `PORT` را روی مقدار ارائه‌شدهٔ میزبان بگذارید؛ سرور HTTP **قبل از اتصال به تلگرام** روی `0.0.0.0` گوش می‌دهد و `GET /health` هنگام آمادگی و اتصال `200 {"ok":true}` و در غیر این صورت 503 برمی‌گرداند (بقیهٔ مسیرها 404). هیچ کلید یا اطلاعات شخصی در پاسخ نیست.
9. دسترسی خروجی به دیتاسنترهای تلگرام، عدم sleep سرویس، ماندگاری `DATA_DIR` بعد از restart/redeploy و فضای واقعی قابل استفاده را بررسی کنید.
10. با اکانت ادمین `/menu` را باز کنید، مقصد را تنظیم کنید و سناریوی آزمون انتهای این فایل را انجام دهید.

بدون فضای دائمی، نشست و تنظیمات پس از بازسازی سرویس از بین می‌روند. اگر پلن sleep یا خاموشی اجباری داشته باشد، کد نمی‌تواند اجرای ۲۴ ساعته را تضمین کند. **قبل از خرید پلن این موارد را تأیید کنید.**

### آیا GitHub Secrets جای پنل میزبان را می‌گیرد؟ (نه)

مخزن می‌تواند عمومی باشد و GitHub Secrets هم جای امنی برای نگه‌داری مقدار است (رمزگذاری‌شده، در UI خوانده نمی‌شود و به workflowهای Pull Request از fork داده نمی‌شود)، ولی **برنامه روی runner گیت‌هاب اجرا نمی‌شود**؛ روی Botkeep/Faable اجرا می‌شود و آن پلتفرم‌ها محتوای GitHub Secrets را نمی‌خوانند. فقط Environment/Secrets پنل خودشان (یا CLI خودشان) در زمان اجرا به پردازش تزریق می‌شود. پس:

- GitHub Secrets تنها زمانی به این پروژه کمک می‌کند که خودت با GitHub Actions روی VPS خودت مستقر کنی (workflow مقدار را برمی‌دارد و در فایل env سرور می‌نویسد).
- اگر Botkeep/Faable از مخزن build می‌کند، این متغیرها را در پنل خودِ سرویس بگذار، نه در گیت‌هاب.
- **هرگز** نشست را در فایل مخزن، در Repository *Variables* (که خواندنی است)، در `echo` داخل workflow یا در `docker build --build-arg` (که در تاریخچهٔ ایمیج می‌ماند) نگذار.

برای Faable بدون تایپ مقدار در ترمینال (تا در history نماند):

```bash
npm i -g @faable/faable
faable login
# فایل .env.production فقط شامل کلیدها و مقدارهای همین اپ باشد
faable deploy secrets set -f .env.production
# یا فقط نشست، از stdin:
printf 'TELEGRAM_SESSION=%s\n' "$(cat data/session.txt)" | faable deploy secrets set -f -
```

در Botkeep هم متغیرها را در بخش Environment/Secrets همان سرویس بگذار و بعد Restart/Redeploy بزن. **یک نشست را هم‌زمان روی دو میزبان اجرا نکن**: تلگرام ممکن است نشست را باطل کند؛ میزبان دوم را فقط به‌عنوان ذخیرهٔ خاموش نگه دار.

### Faable Cloud و میزبان‌های مشابه

- اگر لاگ دو خط `> telepass@1.0.0 start` و بلافاصله `TELEGRAM_API_ID و TELEGRAM_API_HASH ...` را نشان می‌دهد، یعنی متغیرهای محیطی **روی همان Deployment** تنظیم نشده‌اند (فایل `.env` محلی روی میزبان خوانده نمی‌شود). متغیرها را در بخش Environment/Secrets پروژه بگذارید و یک Deployment جدید بگیرید؛ صرفِ تغییر متغیر روی Deployment قدیمی هم معمولاً restart نمی‌کند.
- اگر پیام `نشست تلگرام موجود نیست` آمد، یعنی کد اجرا شده و فقط نشست کم است: `TELEGRAM_SESSION` را تنظیم کنید (بالا) یا `data/session.txt` را در `DATA_DIR` بگذارید.
- اگر پیام `اتصال به تلگرام برقرار نشد` یا `نشست معتبر نیست` آمد، نشست را دوباره بسازید؛ همچنین مطمئن شوید میزبان خروجی TCP به دیتاسنترهای تلگرام را نمی‌بندد.
- «Runtime crash» در پنل با «Build failed» فرق دارد: اینجا build موفق است و پردازش Node به‌خاطر پیکربندی (env/session/port) خارج می‌شود. اصل پیام فارسی انتهای لاگ Runtime را بخوانید، نه فقط هشدار `ExperimentalWarning`.

### بودجهٔ منابع

- `npm start` سقف heap جاوااسکریپت را ۱۶۰ MB می‌گذارد؛ این سقف کل RSS پردازش نیست.
- وابستگی‌های نصب‌شده در محیط آزمون حدود **۱۰ MB** بودند؛ فایل رسانه‌ای ذخیره نمی‌شود. فایل اصلی SQLite با page size پیش‌فرض 4KB حداکثر ۶۴ MiB تنظیم شده است؛ WAL، فضای موقت و لاگ جدا هستند.
- صف ۵۰۰۰ کار و پاک‌سازی ساعتی نتایج برای مصرف محدود طراحی شده‌اند. نرخ بلندمدت بالاتر از حدود یک پیام در ۱٫۲ ثانیه یا FloodWait طولانی، صف را پر می‌کند. هر ریپلای همراه اصل پیام ممکن است دو کار ایجاد کند.
- در صف پر، رویداد جدید پذیرفته نمی‌شود؛ شمارنده در `/status` و کد `QUEUE_FULL` در لاگ قابل مشاهده است. بازیابی خودکار این رویدادها وجود ندارد.
- با ۵۱۲ MB RAM و نیم هسته، بار سبک/متوسط هدف طراحی است؛ ظرفیت واقعی با تعداد گروه‌ها و ترافیک متفاوت است و باید روی میزبان پایش شود. **بنچمارک زندهٔ تلگرام روی این پلن انجام نشده است.**
- اگر ۵۰۰ MB شامل خود سیستم‌عامل/ایمیج هم باشد، جا شدن Node/Docker تضمین‌شده نیست؛ اجرای بومی Node معمولاً انتخاب سبک‌تری است. لاگ میزبان را با rotation محدود کنید.

## Docker (در صورت پشتیبانی میزبان)

```bash
cp .env.example .env
# .env را تکمیل کنید
mkdir -p data
# ایمیج با کاربر node و UID 1000 اجرا می‌شود؛ مالکیت mount باید مناسب باشد.
# در میزبان لینوکسی و در صورت نیاز:
sudo chown -R 1000:1000 data
chmod 700 data
chmod 600 .env
docker compose build
docker compose run --rm telepass npm run login
docker compose up -d
docker compose logs --tail=50 -f
```

Compose محدودیت RAM=512MB، CPU=0.5، چرخش لاگ، volume و `restart: unless-stopped` دارد. هنگام اجرای login سرویس اصلی باید متوقف باشد. برای health check بیرونی پورت را صریحاً در Compose منتشر کنید؛ پیش‌فرض هیچ پورتی منتشر نمی‌شود. در آپدیت، volume را حذف نکنید (`down -v` نزنید).

## سرور لینوکسی با systemd

نمونه در `telepass.service` است؛ مسیر نصب `/opt/telepass`، کاربر سرویس `telepass` و مسیر Node `/usr/bin/node` فرض شده‌اند. ابتدا کاربر سرویس و پوشه را بسازید، پروژه و وابستگی‌ها را نصب و مالکیت را تنظیم کنید. فایل `.env` باید برای همان کاربر قابل خواندن باشد. ورود اولیه را با همان کاربر و مسیر کاری انجام دهید، سپس:

```bash
sudo cp telepass.service /etc/systemd/system/telepass.service
sudo systemctl daemon-reload
sudo systemctl enable --now telepass
sudo journalctl -u telepass -n 50 --no-pager
```

مسیر و نسخهٔ واقعی Node، مجوزهای `data/` و محدودیت journald را بررسی کنید. systemd بعد از خطا با فاصلهٔ ۳۵ ثانیه restart می‌کند؛ خطای ورود/تنظیمات به دخالت شما نیاز دارد.

## پایداری، حریم خصوصی و محدودیت‌ها

- نشست همان لاگین تلگرام است؛ مالک سرویس و هر کس با دسترسی به فایل می‌تواند به اکانت دسترسی داشته باشد. روی هاست غیرقابل اعتماد مستقر نکنید. دسترسی فایل‌ها/پوشه‌ها به‌ترتیب 600/700 تنظیم می‌شود؛ دیتابیس در حالت سکون رمزگذاری داخلی ندارد. برای رمزگذاری، از دیسک رمزگذاری‌شدهٔ میزبان استفاده کنید.
- قفل فایل فقط روی فایل‌سیستم مشترک کار می‌کند؛ نشست یکسان را روی دو سرور با دیسک جدا هم‌زمان اجرا نکنید. برای هر اکانت یک `DATA_DIR` مستقل لازم است.
- اتصال مجدد شبکه خودکار است، اما رد شدن نشست/Logout/بسته شدن اکانت به ورود مجدد نیاز دارد. برای تغییر شمارهٔ اجراکننده، از پوشهٔ دادهٔ جدید استفاده کنید؛ دیتابیس قدیمی به ID اکانت قبلی قفل است.
- صف پذیرفته‌شده بعد از restart باقی می‌ماند. `random_id` ثابت، تکرار ارسال بر اثر retry را با سازوکار تلگرام کاهش می‌دهد؛ **تضمین مطلق exactly-once و عدم از دست رفتن تحت هر نوع خرابی وجود ندارد**. رکوردهای dedup هم retention محدود دارند.
- این سرویس **رصد زنده** است، نه آرشیوگیر. تاریخچهٔ زمان خاموشی/توقف به‌صورت تضمینی بازخوانی نمی‌شود. کتابخانه ممکن است وقفه‌های کوتاه اتصال را جبران کند، اما برای پیام‌هایی که قبل از ورود به صف از دست رفته‌اند SLA بازیابی ندارد.
- محتوای دارای Restrict Saving / protected content فوروارد نمی‌شود و هیچ کپی یا دانلودی برای دور زدن محدودیت انجام نمی‌شود. حذف پیام اصلی، فقدان دسترسی، محدودیت پیوی یا حقوق ارسال هم ممکن است مانع ارسال شود؛ `/errors` را بررسی کنید.
- پس از ۱۰ شکست غیرزمانی، کار به حالت failed می‌رود؛ FloodWait با زمان اعلام‌شده و حاشیهٔ ۲ ثانیه دوباره امتحان می‌شود و شمارندهٔ تلاش را زیاد نمی‌کند. مهلت انتظار ارسال مستقل از کارها در SQLite ذخیره می‌شود و با حذف قانون، پاک‌کردن صف یا ری‌استارت از بین نمی‌رود. کار failed خودکار مجدداً صف‌بندی نمی‌شود.
- پیام‌های سرویس، ویرایش/حذف پیام، پست زمان‌بندی‌شدهٔ هنوز ارسال‌نشده و بک‌فیل تاریخچه پوشش داده نمی‌شوند. پیام‌های رسانه‌ای فوروارد می‌شوند؛ اجزای آلبوم فعلاً جداگانه ارسال می‌شوند و گروه‌بندی آلبوم حفظ نمی‌شود.
- داشتن اجازهٔ قانونی و رضایت لازم برای بازنشر پیام‌ها مسئولیت بهره‌بردار است. فقط در گفتگوهایی که مجاز به دسترسی/بازنشر هستید استفاده کنید. رفتار خودکار ممکن است تحت محدودیت‌های ضداسپم و شرایط تلگرام قرار گیرد؛ دور زدن آن‌ها انجام نمی‌شود.

### پشتیبان‌گیری و بازیابی

سرویس را کامل متوقف کنید، سپس **کل `DATA_DIR`** را با روش امن پشتیبان بگیرید. SQLite باز را با کپی تکی فایل اصلی پشتیبان نگیرید؛ فایل‌های WAL/SHM ممکن است هنوز داده داشته باشند. هنگام انتقالِ نسخهٔ متوقف‌شده، پوشهٔ موقت `session.txt.lock/` و فایل `session.txt.tmp` را منتقل نکنید. مقصد باید از همان اکانت و API credentials استفاده کند. پس از انتقال مجوزهای پوشه و فایل را اصلاح و فقط یک نمونه را اجرا کنید.

اگر پیام‌های فارسی زیر را دیدید:

| پیام | معنی و راه‌حل |
| --- | --- |
| `TELEGRAM_API_ID و TELEGRAM_API_HASH معتبر نیستند` | متغیرها روی همان سرویس/Deployment تنظیم نشده‌اند یا `.env` سمت میزبان خوانده نمی‌شود؛ مقدارها را بدون گیومه در Environment بگذارید و سرویس را restart کنید. |
| `نشست تلگرام موجود نیست` | `TELEGRAM_SESSION` را تنظیم کنید یا `DATA_DIR/session.txt` را بگذارید (روی میزبان بدون ترمینال، `npm run login` اجرا نمی‌شود). |
| `TELEGRAM_SESSION معتبر نیست` | رشتهٔ نشست ناقص کپی شده؛ دوباره `npm run login -- --print-session` بگیرید و کل رشته (بدون فاصلهٔ اضافه) را بگذارید. |
| `TELEGRAM_SESSION با نشست ذخیره‌شده ... یکسان نیست` | هر دو منبع نشست وجود دارند و فرق می‌کنند؛ `session.txt` قدیمی را حذف یا `TELEGRAM_SESSION` را با آن هماهنگ کنید. |
| `اتصال به تلگرام برقرار نشد` | نشست باطل/ناقص است یا میزبان خروجی به دیتاسنترهای تلگرام را می‌بندد. |

برای نشست باطل‌شده: سرویس را متوقف کنید، با `npm run login` وارد همان اکانت شوید و دوباره سرویس را اجرا کنید. در صورت افشای نشست، ابتدا از تنظیمات Devices تلگرام آن نشست را لغو کنید و سپس نشست جدید بگیرید.

## تست و بررسی

```bash
npm ci
npm run check
npm audit --omit=dev
```

تست‌ها بدون تماس با تلگرام و بدون شماره/کلید واقعی اجرا می‌شوند؛ شامل احراز ادمین، منو، فیلتر، toggleها، ریپلای، هویت کانال، لینک‌ها، access hash، SQLite پس از restart، سقف و تراکنش صف، dedup، ترتیب فوروارد، FloodWait، retry، restricted content و قفل تک‌پردازشی‌اند. عبور پیام‌های واقعیِ ساخته‌شده از کلاس‌های MTProto از مسیر dispatch کتابخانه نیز آفلاین آزمایش می‌شود. CI برای Node 22 و 24 تعریف شده است.

نتیجهٔ بررسی محلی در ۲۰۲۶-۱۰-۲۱:

- هر **۴۲ تست** (شامل rollback حذف قانون/مبدأ، حفظ FloodWait بعد از پاک‌کردن صف و اصلاح مجوز نشست منتقل‌شده) روی Node.js **22.22.3** و **24** موفق شدند؛ syntax تمام فایل‌های JavaScript بررسی شد.
- `npm audit --omit=dev`: بدون آسیب‌پذیری شناخته‌شده در زمان بررسی.
- آزمون آفلاین با کلاینت ساخته‌شده و ۵۰۰۰ کار منتظر: RSS حدود **۱۱۴ MB**، فایل اصلی SQLite حدود **۶۴۳ KB**؛ این عدد شامل اتصال/ترافیک زندهٔ تلگرام نیست و معیار تضمین‌شدهٔ ظرفیت نیست.
- اجرای بدون نشست، بدون متغیرهای API، با پوشهٔ دادهٔ غیرقابل‌نوشتن و ورود بدون ترمینال تعاملی با پیام راهنمای فارسی و exit code ناموفق متوقف شدند.
- خواندن نشست از `TELEGRAM_SESSION`، رد کردن رشتهٔ ناقص/خراب و تعارض با `session.txt` تست شد؛ سرور health پیش از اتصال به تلگرام روی پورت گوش می‌دهد.
- اجرای Docker/systemd، ورود واقعی و ماندگاری دیسک botkeep در این محیط آزمایش نشده‌اند.

**تست سرتاسری با اکانت واقعی و خود botkeep.cloud انجام نشده**؛ این تست‌ها جایگزین آن نیستند. پیش از بهره‌برداری این موارد را با دو/سه اکانت آزمایشی خودتان بررسی کنید:

1. دستور از اکانت غیرادمین و داخل گروه → بدون پاسخ/تغییر تنظیمات.
2. پیام شخص مجاز در مبدأ → فوروارد؛ شخص غیرمجاز یا گروه غیرمبدأ → بدون فوروارد.
3. `forwards off/on` → پیام فورواردشده حذف/ارسال شود.
4. `replies on/off` → اصل پیام قبل از پاسخ ارسال شود/فقط پاسخ ارسال شود.
5. کانال هم در مبدأ و هم در وایت‌لیست → پست‌های آن طبق toggle ارسال شوند.
6. restart با صف منتظر → قوانین و صف حفظ شوند؛ فضای دائمی پس از redeploy هم باقی بماند.
7. حذف مبدأ/قانون، توقف/ادامه، تغییر مقصد و عدم مجوز ارسال → خروجی و خطای مورد انتظار.
8. چند ساعت پایش `/status`، مصرف دیسک و لاگ میزبان تحت بار واقعی، قبل از اتکای ۲۴ ساعته.
